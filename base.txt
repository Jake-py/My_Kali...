LeakCheck — это открытый (Public) API для проверки утечек по идентификатору, без ключа, бесплатно, даже для коммерческого использования. По сути — конкурент/дополнение к HaveIBeenPwned, только без обязательной регистрации API-ключа для базового тира.

## Как это работает

```
GET https://leakcheck.io/api/public?check={query}
```

Один параметр — `check`. Сервис сам определяет тип запроса:

| Тип | Формат | Комментарий |
|---|---|---|
| Email | `user@example.com` | напрямую |
| Email по хешу | `31c5543c1734d25c7206f5fd` | SHA256, обрезанный до 24 символов — способ проверить свой email, не отправляя его в открытом виде |
| Username | `example` | минимум 3 символа |

## Что важно понимать про **бесплатный** тир

Это не полноценный дамп утечки — это **разведка о разведке**. Ответ говорит:
- **сколько раз** идентификатор засветился (`found`)
- **в каких категориях данных** он был скомпрометирован (`fields`: username, first_name, address...)
- **в каких именно утечках** (`sources`: имя базы + дата)

Но **сами данные** (пароли, реальные адреса, хеши) не возвращаются — за этим нужен Pro API. Это разумное разделение: бесплатный тир годится для быстрого "проверить, засветился ли этот таргет хоть где-то", а не для полного разбора утечки.

## Лимит и условия

- **1 запрос в секунду** — жёстко. Если планируете батчить много идентификатором подряд (например, список email после SpiderFoot-разведки) — нужен `sleep(1)` между вызовами, иначе поймаете троттлинг.
- Условие использования — если светите результаты публично (на сайте), нужна атрибуция "Powered by LeakCheck". Для личного инструмента, который не выходит за пределы вашей машины — не критично, но раз вы человек с совестью в кибере (сами сказали), пусть это будет мелкая деталь, о которой вы знаете.

## Как это ложится в вашу архитектуру

Прямая находка — эта штука отлично встаёт в вкладку **"Аккаунты"**, рядом с Sherlock/Maigret: тот же паттерн "идентификатор → присутствие в источниках", только источники — это утечки, а не соцсети. Никаких внешних бинарников ставить не надо — чистый HTTP-запрос, значит адаптер получается даже проще, чем для CLI-инструментов:

```python
import requests
import time

class LeakCheckAdapter:
    BASE_URL = "https://leakcheck.io/api/public"
    _last_call = 0

    def run(self, identifier: str) -> dict:
        # уважаем rate limit в 1 req/sec
        elapsed = time.time() - self._last_call
        if elapsed < 1:
            time.sleep(1 - elapsed)

        try:
            resp = requests.get(self.BASE_URL, params={"check": identifier}, timeout=10)
            self._last_call = time.time()
            resp.raise_for_status()
            data = resp.json()
        except requests.RequestException as e:
            return {"status": "error", "raw_output": None, "parsed_data": None, "error": str(e)}

        if not data.get("success"):
            return {"status": "error", "raw_output": data, "parsed_data": None, "error": "API returned success=false"}

        return {
            "status": "ok",
            "raw_output": data,
            "parsed_data": {
                "found_count": data.get("found", 0),
                "exposed_fields": data.get("fields", []),
                "sources": data.get("sources", []),
            },
            "error": None,
        }
```

Это ровно тот контракт `{status, raw_output, parsed_data, error}`, о котором мы говорили в связи с адаптерным слоем — только тут вместо `subprocess.run()` внутри HTTP-запрос. Один и тот же UI-обработчик "результат карточки" сможет отрисовать и вывод Sherlock, и вывод LeakCheck, не зная о разнице реализации внутри

1
Зависимости и конфигrequests, скорее всего, уже стоит — остальные ваши тулы через subprocess, а этот через HTTP. Добавьте таймаут и rate-limit как константы конфига (не хардкод внутри функции), чтобы потом не искать их по всему коду, если LeakCheck поменяет лимит.
2
Адаптер как отдельный модульВынесите LeakCheckAdapter в свой файл (adapters/leakcheck.py или как у вас организовано), а не внутрь обработчика кнопки. Контракт {status, raw_output, parsed_data, error} должен быть идентичен остальным адаптерам — это то, что вы уже проектируете для стабильности всего приложения, LeakCheck просто первый кандидат.
3
Валидация ввода до отправки запросаДокументация требует минимум 3 символа для username. Проверяйте длину и базовый формат (email regex или просто наличие '@') на стороне клиента, до сетевого запроса — иначе тратите впустую 1 запрос в секунду на заведомо провальный вызов и злите rate limit почём зря.
4
Изоляция в поток (QRunnable/QThread)Обработчик кнопки создаёт worker, worker шлёт сигнал с результатом обратно в UI-поток. Никогда не трогайте виджеты напрямую из фонового потока в PySide6 — это либо тихий баг, либо падение приложения в самый неподходящий момент.
5
Различение уровня критичности находки в UIЕсли в 'fields' есть password, ssn, credit_card — выводите отдельным красным блоком, а не в общем списке наравне с city или zip. Одна утечка с паролем весит больше, чем десять утечек с одним только именем пользователя — UI должен это показывать, а не просто перечислять поля алфавитным списком.
6
Обработка нулевого результата отдельно от ошибкиfound: 0 — это не ошибка, это хорошая новость (идентификатор нигде не засветился). Не путайте с status: error в вашем адаптере — иначе пользователь увидит красный крест там, где должна быть зелёная галочка 'утечек не найдено'.
7
Бейдж статуса источника, как у остальных инструментов[Online] / [Недоступен] — та же визуальная система, что у [Kali OK] / [Не установлен]. Проверяйте доступность коротким HEAD-запросом или просто по результату последнего вызова, не отдельным постоянным пингом — незачем тратить лишний запрос в секунду на health-check, когда лимит и так всего 1/сек.
8
Тест на граничных случаях перед тем, как считать готовымПрогоните: (1) email с 2000+ находками, как в моём тесте — не подвиснет ли рендер длинного списка sources; (2) полностью чистый идентификатор без утечек; (3) username короче 3 символов — проверьте, что клиентская валидация ловит это раньше сети; (4) отключите Wi-Fi на 10 секунд и нажмите запуск — приложение должно показать ошибку сети, а не зависнуть.



Пункт 6 — самый коварный. Разработчики почти всегда тестируют на "известном грязном" идентификаторе (вроде example@example.com, который я только что дёрнул) и радуются, что всё работает. А потом первый же реальный пользовательский ввод с found: 0 рисует красный крест ошибки вместо зелёной галочки "чисто" — потому что где-то в коде if not result: show_error() вместо if result.status == "error": show_error(). Разные вещи.

Пункт 8, тест номер 4 — отключение сети специально. Проверить работающий сценарий все делают, а сценарий "сеть просто исчезла на середине запроса" — почти никогда, а именно он чаще всего роняет самодельные GUI. requests.exceptions.ConnectionError — отдельный тип исключения, отличный от таймаута, убедитесь, что ваш except requests.RequestException его ловит (он ловит, ConnectionError — подкласс, но проверить руками дешевле, чем доверять на слово документации библиотеки).
